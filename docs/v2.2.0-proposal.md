# Precision-MOD v2.2.0 — Release Proposal

**Status:** released as v2.2.0 (this document records the rationale and trade-offs for future audit)
**Source rulebook:** v2.1.0 (commit `4b1cfea` on `main`)
**Target rulebook:** v2.2.0
**Created:** 2026-05-08
**Origin agent:** claude (opus-4-7-1m)

## Context

Precision-MOD v2.1.0 has been used in production across several real projects. Six recurring failure modes surfaced that the rulebook did not patch. Each failure was screened with the universal-rulebook test:

> *Does this make sense in a Rust embedded project? A solo Python script? A Java enterprise monorepo?*

Practices that failed that test (DBI-METADATA, browser-testing as hard-lock, pandoc-based weekly reports, severity scales, stack discriminators, region-specific data regulations) are **not** in this release. They remain in adopting projects' own `codebase_rules.md`, which is exactly where the universal rulebook says they belong.

## Six rules — failure modes patched

| Failure mode | Patch |
|---|---|
| Agent infers prod approval from a "yes" answer in a multi-part prompt | §2.3 Production Boundary |
| Sensitive values (PII, financial IDs, internal data) leak into commits/plans/bug reports — §2.2 only covered credentials | §2.4 Sensitive Data Handling |
| Agent uses raw CLI (`docker exec`, `kubectl`, `psql`) instead of project-provided wrappers | §7 extension — Mandatory Tooling Wrappers |
| Tasks marked "complete" with confidence rather than evidence | §9 extension — Verification Gates |
| Silent breakage of sibling repos (deploy scripts, infra, generated clients) | §14 Cross-Repository Impact |
| Bug/feature history scattered across external trackers, chat, PR descriptions; lost on tracker migration | §15 In-Repo Issue Tracking (opt-in) |

All six defer concrete enumeration to per-project `codebase_rules.md`. The rulebook standardizes the convention; the project owns the vocabulary.

## Design constraints honoured

- **Codebase-agnostic.** No tool, framework, regulation, stack, severity scale, or template named in the rulebook body.
- **Non-breaking.** No previously-valid rule becomes invalid.
- **§15 explicitly opt-in.** Projects preferring external-tracker-only workflows are unaffected.
- **Layered with existing rules.** §2.3 and §2.4 sit beside §2.1 (Git Safety) and §2.2 (Credential Management) under Golden Rules. §7 and §9 are extensions of existing sections. §14 and §15 are new top-level sections appended.

## Hardening applied during review

The first draft was reviewed and the following gaps closed before release:

| Gap | Resolution |
|---|---|
| §2.3 protected against ambiguous user "yes", but not against the agent itself bundling prod with non-prod actions | Added the contrapositive: agent SHOULD NOT bundle prod actions with non-prod actions in the same confirmation prompt |
| §7 wrapper rule had no escape valve when the wrapper was missing a feature, broken, or being modified | Added explicit notify-and-authorize fallback before falling through to the underlying CLI |
| §9 verification gate forced gates onto investigative/read-only tasks where no concrete gate exists | Distinguished state-changing tasks (concrete gate) from investigative tasks (exit criterion) |
| §14 left "completion" notification ambiguous between chat-time signal and tracked-artefact marker | Clarified: chat-time signal only; not required in commit messages or tracked artefacts |
| §15 bug reports/analysis could legitimize sensitive data in tracked artefacts | Cross-referenced §2.4 anonymization explicitly inside §15 |
| §15 was silent on issues that span multiple repositories | Added one-line rule: folder lives where the fix is implemented; siblings reference by path |
| §15 was the longest section in the rulebook (~80 lines) for an opt-in convention | Trimmed redundant lifecycle table and the "what the project defines" recap; ~30 lines saved |

## What is intentionally NOT in this release

Considered and deferred because they were not universal:

- Specific issue templates (bug body schema, PRD format, pre-fix/post-fix checklists)
- Patch lifecycle conventions (assumes relational DB + migration tooling)
- Browser-testing requirements (assumes web UI)
- Severity scales (Critical/High/Medium/Low)
- Stack discriminators in folder names
- Stakeholder reporting workflow
- Region-specific data regulation language (RGPD, HIPAA, PCI)
- Specific document-generation toolchains (e.g., `pandoc md → docx`)

These remain in adopting projects' own `codebase_rules.md`.

## Migration

Projects on v2.1.0 upgrade non-breaking. To tighten enforcement project-by-project, add to `AI_Guidelines/codebase_rules.md`:

1. Production-flagged targets (§2.3)
2. Sensitive data categories and placeholder schemes (§2.4)
3. Privileged tooling wrappers (§7)
4. Default verification gates and exit-criterion templates (§9)
5. Sibling repositories and cross-repo sync points (§14)
6. Issue folder conventions if adopting §15 (ID format, required files, lifecycle states, severity)

The rulebook itself works without these additions; the additions tighten enforcement.
